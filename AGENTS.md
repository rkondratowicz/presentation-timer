# Agent Guidelines

## Product and Constraints

Read [README.md](./README.md) before changing behavior. It documents supported behavior and manual validation; this file governs implementation.

- Build a small, dependable browser app, not a platform.
- Use semantic HTML, CSS, and vanilla JavaScript ES modules.
- No frameworks, bundlers, build step, backend, native app, or automated test suite.
- No PWA installation, service worker, or offline-launch infrastructure.
- Prefer native browser capabilities. Do not add dependencies or development tooling without a concrete need and user agreement.
- Serve through HTTP locally and HTTPS in production; do not rely on opening files directly.

## Code Quality

- Choose the simplest complete solution. Modern code means clear, correct, accessible, and maintainable, not more abstractions.
- Use small, cohesive modules with explicit imports/exports. Separate timer calculations and transitions, DOM rendering, and browser integrations.
- Keep one authoritative session state. Derive display values and warning levels instead of maintaining competing copies.
- Keep calculations and state transitions free of DOM, storage, and clock reads. Pass the current time into logic that needs it.
- Use explicit states and enforce their invariants. Do not allow impossible combinations or silently substitute defaults for invalid session state.
- Use descriptive names, consistent units (`Ms` for milliseconds), `const` by default, and strict comparisons.
- Add concise JSDoc only where data shapes, units, or contracts need clarification. Comment why, not what the code already says.
- Do not add speculative abstractions, generic event buses, custom component systems, or configuration for hypothetical features.
- Follow existing conventions, keep changes focused, and preserve unrelated work. Update the README when agreed behavior changes.

## Timing and Browser Reliability

- Follow the README's elapsed-time model. Refresh callbacks are not clocks; never decrement a counter on each tick.
- Keep full precision internally and round only for display.
- Make rendering safe to repeat; it must not start timers, register listeners, save state, or request browser capabilities.
- Own and clean up intervals, listeners, and wake-lock handles. Repeated start/reset cycles must not accumulate work.
- Handle visibility changes, reload recovery, and optional API failures explicitly. Do not assume desktop behavior matches iPad Safari.
- Validate persisted data before use and version its format. Treat storage as fallible.
- Catch errors at meaningful boundaries, such as storage and browser API calls. Explain actionable failures in the UI; no empty catches or success-shaped fallbacks.
- A failed optional feature must not stop the timer. Keep the UI honest about what is unavailable.

## HTML, CSS, and Accessibility

- Use native buttons, inputs, labels, and dialogs where appropriate. Do not recreate native controls with clickable generic elements.
- Keep keyboard operation, visible focus, accessible names, and sensible focus restoration intact.
- Do not announce the timer every second to screen readers; announce meaningful status changes.
- Use CSS custom properties for themes and warning treatments, with layout separated from state styling.
- Use tabular digits and stable dimensions so numbers, warnings, and controls do not jump.
- Respect reduced-motion preferences. Never rely on color alone to convey urgency.
- Design for touch and constrained tablet viewports in both orientations; account for safe areas and changing browser chrome.
- Keep application code in external modules and use DOM text/property APIs rather than injecting HTML from input or saved data.

## Validation and Handoff

- No automated test suite or test-runner dependencies. Use manual browser checks and interactive browser tools.
- After functional changes, exercise the changed behavior and adjacent transitions in a real browser. Check for console errors.
- Use the checklist in [README.md](./README.md#manual-browser-validation) for complete validation; pay special attention to exact deadline boundaries, pause/resume, duration edits, and recovery.
- Check responsive layouts, keyboard behavior, themes, and failure paths when affected.
- Validate responsive layouts in portrait and landscape using browser viewport resizing or emulation. Actual iPad Safari testing is not required; do not claim desktop checks verify device-specific behavior.
- Never claim checks passed unless performed. Report what was checked, what remains unverified, and any device/tool limitations.
- Do not leave temporary files or validation-only processes behind. Summarize the changes and validation concisely.

## Commit and PR Messages

- Never add `Co-authored-by` trailers, AI attribution, "generated by" notices, assistant signatures, or promotional text to commits or pull request descriptions.
- Keep messages focused on the actual changes and validation.
